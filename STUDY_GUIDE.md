# Phishing Email Analyzer — A Study Guide

*Learn how this website is built, one idea at a time. No prior coding knowledge needed.*

1. Open the folder **Phishing-Email-AnalyserV2**.
2. Inside are three files. You can open any of them with **Notepad** (right-click a file → *Open with* → *Notepad*) to see the real code.
3. Read one section below, then look at that part of the code. **Reading the real code next to the explanation is the fastest way to learn.**

The three files are:

| File | Job | Plain-English idea |

## Part 1 — The big idea: three languages, three jobs

A web page is built from three "languages", and each has exactly one job:

1. **HTML** = structure. It says "there is a heading, a button, and a box to type in." Think of it as the **walls and rooms of a house**.
2. **CSS** = style. It says "the heading is big and white, the button is blue." Think of it as the **paint, wallpaper and furniture**.
3. **JavaScript (JS)** = behaviour. It does the work: "when the user clicks, read the text, count the warning signs, show a score." Think of it as the **electricity and plumbing** that make things happen.

The three files talk to each other using **names**:

- HTML gives an element a **`class`** (a group name, like "dog" — there can be many) or an **`id`** (a unique name tag, like "my-dog" — there is only one).
- CSS uses those class names to decide how things look.
- JavaScript uses those ids to *find* elements and change them.

> Example: in `index.html` there is a button with `id="analyse-btn"`.
> In `script.js`, the code says `document.getElementById("analyse-btn")` — which means "find the thing with the id 'analyse-btn'" — and then attaches a click handler to it.

## Part 2 — What happens when you open the page

1. Your browser downloads `index.html`.
2. Near the top of that file, there is a line that says *"also load `styles.css`"* and, near the bottom, a line that says *"also load `script.js`"*.

## Part 3 — Inside `index.html` (the skeleton)

The whole page is made of **tags**. A tag looks like this:

```html
<h2>Analyze an Email</h2>
```

- `<h2>` means "a heading".
- The text between the tags is what the user sees.
- `</h2>` closes the tag (the `/` means "end").

### Tags you will see in this project

- `<h1>`, `<h2>`, `<h3>` — headings (big, medium, small).
- `<p>` — a paragraph of text.
- `<a>` — a link (the `href` says where it goes).
- `<button>` — a clickable button.
- `<textarea>` — a big box you can type lots of text into.
- `<section>` — a whole "page" of content.
- `<div>` — a general-purpose box used to group things.

### Classes vs ids

- `class="..."` is a **group label**. Many elements can share the same class.
- `id="..."` is a **unique name**. Only one element on the page should have that id.

The analyser section is `<section class="section" id="analyser">`. It has both: a class (`section`) for styling, and an id (`analyser`) so JavaScript (and links) can find it.

## Part 4 — Inside `script.js` (the brain)

This is the most important file to understand, because it holds the *intelligence*.

### 4.1 The wrapper (an "IIFE")

At the very top of `script.js` you will see:

```js
(function () {
  "use strict";

  // ... all the code ...

})();
```

This is called an **IIFE** (say it "iffy"). It just means: "run all this code immediately, and keep it self-contained." It stops this page's variables from mixing with any other script's variables. You don't need to change it — just know it's a protective wrapper.

### 4.2 Variables, arrays and objects (the building blocks)

- A **variable** is a named box that holds a value. Example: `const score = 75;` stores the number 75 in a box called `score`.
- An **array** is a list. Example: `[1, 2, 3]` is a list of three numbers. The demo emails are stored in a list called `DEMO_EMAILS`.
- An **object** is a box of related named things. Example:

```js
{
  id: "obvious",
  name: "Obvious phishing",
  points: 30
}
```

- A **function** is a reusable recipe. You give it inputs, it does work, and (usually) returns an output.

### 4.3 The demo emails

Look for `DEMO_EMAILS` near the top. It is an **array of objects** — a list where each item describes one example email (its name, a short description, and the email text itself). When the page loads, JavaScript loops over this list and creates one card per item.

### 4.4 The heart of it: the detectors

The whole "intelligence" is a list of **detectors**. Each detector asks one yes/no question about the email text, like:

> "Does this text ask for a password?"

Each detector has:
- a **title** (what it's called),
- a **number of points** (how serious it is),
- a **description** (the plain-English explanation shown to the user), and
- a **check** — the actual rule that searches the text.

The most important concept here is the **regular expression** (or **"regex"** for short).

#### What is a regex?

A regex is a **pattern that searches text**. It's like a very flexible "find" in a word processor.

For example, the urgency detector uses a pattern that matches words like:

```
urgent | immediately | asap | act now | final warning | within 24 hours
```

In JavaScript, a regex is written between two `/` slashes. The letters `i` and `g` at the end are **flags**:

- `i` = "ignore upper/lower case" (so "URGENT" and "urgent" both match).
- `g` = "global" (find *all* matches, not just the first one).

Here is a tiny real example from the code:

```js
/\b(urgent|immediately|asap)\b/i
```

This means: *"find the word 'urgent', OR 'immediately', OR 'asap' (any capitalisation), as a whole word."*

- `\b` means "word boundary" (so it won't match the middle of another word).
- `|` means "or".
- `()` groups the choices together.

> Learning regex is the single most useful skill for writing a phishing detector. It is a whole mini-language of its own, but you can start with just "words separated by `|`".

### 4.5 How a detector is written (two kinds)

1. **Simple word detectors** — most detectors just search for keywords. The code has a helper called `regexDetector(...)` so it doesn't have to repeat the same code 15 times. Example:

```js
const DET_PASSWORD = regexDetector(
  "password", "Asks for your password or login details", 30,
  "It asks you to provide, verify, or enter your password...",
  /\b(verify your password|confirm your password|enter your password)\b/gi
);
```

2. **Custom detectors** — some checks need more than a word search. For example, the "suspicious URL" check must *find links, then inspect each one* (is it `http`? does it pretend to be a known brand? does it use an IP address?). Those are written as their own `check` function instead of using `regexDetector`.

## Part 5 — How the score is calculated (the "explainable" part)

This is the key to the whole design: **there is no mystery number.**

Every warning sign is worth a fixed number of points. The code adds up all the points for the warning signs it finds, caps the total at 100, and gives it a label.

### The full scoring table

| # | Warning sign | Points | What it looks for |
|---|-------------|:------:|-------------------|
| 1 | Urgency & pressure language | 10 | "act now", "within 24 hours", "final warning" |
| 2 | Threat to suspend/close account | 20 | "your account will be suspended/closed" |
| 3 | Asks for your password | 30 | "verify/confirm/enter your password" |
| 4 | Asks for a verification/MFA code | 25 | "verification code", "one-time code", "2FA" |
| 5 | Payment or gift-card request | 25 | "gift cards", "wire transfer", "bitcoin" |
| 6 | Change bank/payment details | 25 | "our bank details have changed", "sort code" |
| 7 | Unexpected invoice | 10 | "invoice", "overdue", "past due" |
| 8 | Credential harvesting | 15 | "verify/confirm/update your account" |
| 9 | Impersonation language | 10 | "Dear Customer", "security team" |
| 10 | Shortened link | 15 | "bit.ly", "tinyurl", "goo.gl" |
| 11 | Enable macros | 25 | "enable macros", ".docm" |
| 12 | Executable attachment | 25 | ".exe", ".bat", ".scr", ".js" |
| 13 | Unusual attachment filename | 10 | archives, "invoice.pdf", double extensions |
| 14 | Suspicious / risky link | 15 | http (not https), lookalike brand |
| 15 | Raw IP-address link | 25 | a link straight to numbers like 192.0.2.10 |
| 16 | Misleading link text | 15 | text says one site, link goes elsewhere |
| 17 | Sender vs Reply-To mismatch | 20 | *only if headers are pasted* |
| 18 | SPF failed | 15 | *only if headers are pasted* |
| 19 | DKIM failed | 15 | *only if headers are pasted* |
| 20 | DMARC failed | 20 | *only if headers are pasted* |
| 21 | No DMARC policy | 10 | *only if headers are pasted* |

### The classification bands

| Score | Label |
|------:|-------|
| 0–34  | **Low Risk** |
| 35–69 | **Suspicious** |
| 70–100| **High Risk** |

### The function that ties it together

Look for `analyseEmail(text)`. It does this:

1. Loops through **every** detector.
2. For each one, asks its `check` question.
3. If it "fires" (matches), adds that detector's points to a running total, and remembers the evidence it found.
4. Caps the total at 100.
5. Returns the score, the classification, the list of findings, and a list of recommendations.

```js
let score = hits.reduce(function (sum, h) { return sum + h.points; }, 0);
if (score > 100) score = 100;
```

`reduce` is just a fancy way to say "add up all the numbers in this list."

## Part 6 — The header checks (SPF / DKIM / DMARC)

When you paste a *full* email (including the hidden "headers"), the tool can do three extra checks. In plain English:

- **SPF** = "is this email really allowed to be sent from that server?" (a whitelist of allowed senders)
- **DKIM** = "does this email's digital signature actually match?" (a tamper-proof seal)
- **DMARC** = "do SPF and DKIM agree, and what should happen if they fail?" (the rule that combines the two)

The code first checks *"does this text even contain headers?"* using a function called `hasEmailHeaders`. It looks for lines that start with things like `From:`, `Received:`, `Authentication-Results:`.

If headers are found, it searches the text for markers like `spf=fail`, `dkim=fail`, and `dmarc=fail`, and also compares the `From:` address to the `Reply-To:` address (a mismatch is a classic trick).

> Security note: these checks are only *as good as the pasted text*. They don't actually connect to any server — they just read what you pasted.

## Part 7 — Why your email never leaves your computer

This is a **privacy-by-design** detail and a great thing to understand:

- There is **no `fetch()`** and **no `XMLHttpRequest`** anywhere in the code. Those are the two JavaScript commands that send data to a server. Without them, the page *cannot* upload anything.
- There is no `<form>` that submits anywhere.
- Everything happens in **memory** inside your browser tab. Close the tab and it's gone.

That's why the site works even with Wi-Fi turned off — it's just files doing calculations locally.

## Part 8 — Inside `styles.css` (the look) — a quick tour

- At the top, under `:root { ... }`, there are **CSS variables** — named colours like `--bg`, `--accent`, `--border`. Changing `--accent` in one place changes the blue everywhere. This is why the whole site can be re-coloured in one edit.
- **`flex`** and **`grid`** are the two layout tools. `grid` makes the cards line up in neat rows; `flex` centres and spaces things.
- **`@media (max-width: 640px) { ... }`** is how the site knows it's on a phone, and applies different spacing.
- **Animations** (`@keyframes`, `transition`, `animation`) create the fade-ins and the hover "lift". Look for `heroIn`, `revealIn`, and `popIn`.
- The reveal-on-scroll works with a JS tool called **`IntersectionObserver`** (in `script.js`), which watches when an element scrolls into view and adds a class that triggers the CSS animation.

## Part 9 — Follow along: what happens when you click "Analyze Email"

Here is the exact journey, step by step. Follow it in the code.

1. **You click the button.** The button has `id="analyse-btn"`. Near the bottom of `script.js` there is:

   ```js
   document.getElementById("analyse-btn").addEventListener("click", runAnalysis);
   ```

   `addEventListener` means "when this is clicked, run the function `runAnalysis`." (This is called an **event listener**.)

2. **`runAnalysis()` reads the text.** It finds the textarea by its id and reads what you typed:

   ```js
   const text = input.value;
   ```

3. **It calls `analyseEmail(text)`** — the brain — which runs all 21 detectors and returns a result object.

4. **It calls `renderResults(result)`** — which builds the HTML for the score circle, the "Warning signs found" list, and the "Recommended actions" list, and puts it on the page using `innerHTML`.

5. **The score circle fills up and counts up.** The circle uses an SVG `<circle>` whose "stroke-dashoffset" is changed by JavaScript to show the score as a partial ring. The number counts up from 0 using `requestAnimationFrame` (a smooth animation loop).

That's the whole app in one paragraph: **listen → read → analyse → render.**

## Part 10 — Glossary (plain English)

| Term | Meaning |
|------|---------|
| **HTML** | The language that says *what* is on a page. |
| **CSS** | The language that says *how it looks*. |
| **JavaScript (JS)** | The language that *does things* (interactivity, logic). |
| **Tag** | A piece of HTML like `<h1>...</h1>`. |
| **Class / id** | Names given to elements so CSS and JS can find them. |
| **Variable** | A named box that holds a value. |
| **Function** | A reusable recipe. |
| **Array** | A list of values. |
| **Object** | A box of related named values. |
| **String** | Text (letters/words), e.g. `"hello"`. |
| **Number** | A number, e.g. `75`. |
| **Regex** | A pattern that searches text. |
| **Flag** | Extra letters (`i`, `g`) that change how a regex works. |
| **DOM** | The "Document Object Model" — the browser's live map of the page, which JS can read and change. |
| **Event listener** | A command that says "when X happens, do Y." |
| **IIFE** | A self-running, self-contained code wrapper. |
| **`fetch()` / `XMLHttpRequest`** | The JS commands that talk to a server (this app has none, for privacy). |
| **SVG** | A way to draw shapes (like the score circle) with code. |

## Part 11 — Ideas to practise (start here!)

The best way to learn is to *change one thing and see what happens*. Try these in order:

1. **Add a new keyword** to a detector. Find `DET_URGENCY` and add another word to its regex, like `|do it now`. Save, refresh, and test the "obvious" example.
2. **Change a point value.** Find `DET_PASSWORD` and change `30` to `40`. See how the score changes.
3. **Add a new demo email.** Copy one item in `DEMO_EMAILS`, give it a new `id`, `name`, `description`, and `body`, and watch a new card appear.
4. **Change the accent colour.** In `styles.css`, change `--accent: #3b82f6;` to `#22c55e` (green) and refresh.
5. **Add a brand to the lookalike list.** Find `BRANDS` in `script.js` and add a new line like `netflix: ["netflix.com"]`. Now a link to "netflix-verify.example" gets flagged.
6. **Trace a real email.** Open the site, click "Open example" on one of the fictional emails, and read each warning sign the tool found — then find the detector that produced it in the code.

> **Pro tip:** When you experiment, always keep a backup copy of the folder first, so you can never "break" it permanently.
